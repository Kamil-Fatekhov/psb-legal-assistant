# Юридический ассистент ПСБ

Проект для трёх участников. Корневой `solution.py` подключает поиск по фрагментам к пакетному запуску стартера. Общие типы находятся в `contracts.py`.

| Кто | Файлы | Первый результат |
| --- | --- | --- |
| A | `knowledge/` | Поиск возвращает полные пункты 3.1 и 3.2 договора «Северный Склад». Просмотр по ID возвращает тот же текст. |
| B | `assistant/`, `solution.py` | Общее ядро принимает вопрос и историю, возвращает выводы с ID источников. Сабмит сохраняет исходный ID вопроса в CSV. |
| C | `web/`, `fixtures/`, Docker | Чат показывает ответ и открывает источники по ID. Без готового ядра работает на моке из `fixtures/rent_case.json`. |

## Стыковка

- `AskRequest.history` идёт от старых реплик к новым и не включает текущий вопрос.
- `SearchQuery.as_of` задаёт дату для выбора редакции. Для условия, зависящего от конкретного события, передавайте также `event_kind` и `event_date`. `AmendmentRule.applies_after` задаёт строгую нижнюю границу даты события.
- Поиск и просмотр работают с одним `Corpus`. ID фрагмента устойчив при повторной сборке того же корпуса. `effective_from` включается в интервал, `effective_to` исключается.
- Каждый `Finding.source_ids` содержит ID подтверждающих фрагментов из выдачи. Отсутствие данных отражается в `Answer`, сбой зависимости передаётся через `DependencyUnavailable`.
- План стыковки предусматривает общий `AssistantService` для чата и сабмита. Пока сабмит формирует текст через вызов генерации из стартера. Проверка выводов и выбор редакции на дату остаются отдельными задачами.

Исходный пример и описание API находятся в [`sample_submission/`](sample_submission/README.md).

## Веб-чат

Одна команда из корня репозитория:

```sh
docker compose up --build
```

Чат открывается на http://localhost:8000. Без базы знаний и ключа он работает в демо-режиме (ответы из фикстуры). Для настоящих ответов положите базу в `data/kb.zip` (или папку `data/kb/`), скопируйте `.env.example` в `.env` и укажите `LLM_BASE_URL` и `LLM_API_KEY`.

| Адрес | Что делает |
| --- | --- |
| `POST /api/chat` | `{question, history}` → `Answer` и список источников. 422 — неверный запрос, 503 — сбой зависимости или ядро не подключено, 502 — ответ без ссылок |
| `GET /api/sources/{fragment_id}` | Точный текст фрагмента и `context_text`. Неизвестный ID — 404 |
| `GET /api/health` | Режим (`mock`/`core`) и число фрагментов |
| `GET /api/docs` | Интерактивное описание API |

Переменные окружения веба: `ASSISTANT_MODE` (`auto`, `mock`, `core`), `DATA_DIR`, `KB_PATH`, `WEB_PORT`, `LOG_LEVEL`, `MOCK_DELAY_MS`. Подробная инструкция, проверки и сценарии демо — в [`docs/web.md`](docs/web.md).

## Прогон сабмита

Подготовьте `data/questions.csv` и `data/kb.zip`. Адрес API и ключ передаются в `LLM_BASE_URL` и `LLM_API_KEY`. Локально можно указать их в игнорируемом файле `.env`. Переменные, переданные платформой, имеют приоритет.

```sh
python solution.py
```

За один прогон скрипт читает ZIP, нарезает документы, строит индекс через `/embeddings` пакетами и переиспользует его для всех вопросов. При сбое эмбеддингов поиск продолжает работать по словам. Если задан `RERANKER_MODEL`, скрипт пересортировывает кандидатов через `/rerank`. При сбое реранкера сохраняет текущий порядок. Генерация получает полные тексты выбранных фрагментов. Ответы записываются в `submission.csv` в порядке входных строк.

В корень ZIP сабмита положите `solution.py`, `contracts.py`, пакет `knowledge/` без локальных файлов и `submission_requirements.txt` под именем `requirements.txt`. Порядок установки зависимостей и параметры API сверяйте с регламентом платформы. Локальные `.env`, `test.py`, `embeddings.npz` и входные данные в архив не входят.
